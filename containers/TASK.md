# Техническое задание для Codex — КОНТ-ЛИДЕР

## Роль и способ работы
Ты — опытный frontend-инженер, UI/UX-дизайнер и специалист по техническому SEO. Реализуй законченный адаптивный коммерческий одностраничный сайт продажи морских контейнеров. Работай непосредственно в текущем репозитории. Сначала изучи проект, версии Node и пакетного менеджера, существующие файлы и конфигурацию. Не удаляй пользовательский код без необходимости. Составь краткий план, затем реализуй по этапам, проверяя результат после каждого этапа. Не утверждай, что что-либо протестировано, если тест не выполнялся. Если отсутствуют реальные материалы или секреты, используй явные заглушки и перечисли, что требуется от заказчика.

## 1. Цель и ограничения
Проект: «КОНТ-ЛИДЕР», сайт продажи морских контейнеров. Основная цель — заявки на покупку и расчёт доставки; вторичные — звонок и переход в мессенджер. Сайт должен выглядеть как работа сильной студии, не как шаблонный AI-лендинг. Это одностраничный коммерческий сайт, а не интернет-магазин: не нужны корзина, личный кабинет, онлайн-оплата, сложная админка. Реальные фотографии клиент пришлёт позднее. Не выдумывай достоверные адреса, цены, телефоны, сроки, статистику, отзывы, гарантии, юридические реквизиты. Все демоданные должны быть очевидно помечены и централизованы. Не публикуй сайт и не выполняй платные действия без разрешения владельца.

## 2. Стек
- Nuxt 4, Vue 3, TypeScript (strict), Composition API, `<script setup lang="ts">`.
- SCSS, нативные CSS Grid/Flexbox, современный адаптивный CSS.
- Nuxt/Nitro server routes для формы заявки, если выбранный хостинг поддерживает серверный runtime.
- Nuxt Image при корректной настройке для выбранного деплоя; иначе нативные оптимизированные изображения с `srcset`/`sizes`.
- ESLint, форматирование, минимальные тесты Vitest при необходимости.
- Не добавлять Tailwind, Bootstrap, Vuetify, Pinia, анимационные фреймворки и крупные UI-библиотеки без доказанной потребности.
- Учитывай фактическую структуру Nuxt 4 (`app/`, `server/`, `public/`), не копируй устаревшие примеры Nuxt 3 без проверки.

## 3. Визуальная концепция
Согласованный стиль: современный промышленный минимализм (Modern Industrial / Editorial Corporate), светлый фон, графитовая типографика, тёмный сине-серый, терракотово-оранжевый CTA, крупные фотографии контейнеров, чистая строгая сетка, умеренная асимметрия, много воздуха. Дизайн должен быть уникальным, но коммерчески понятным.

Ориентировочные токены:
```
--color-bg: #F7F7F4;
--color-surface: #FFFFFF;
--color-surface-alt: #F0F1ED;
--color-text: #202A30;
--color-muted: #626B70;
--color-accent: #C65A36;
--color-accent-hover: #A84629;
--color-dark: #26343B;
--color-border: #DCE0DD;
```
Допустима небольшая корректировка цветов при сохранении направления и WCAG-контраста. Избегать фиолетовых градиентов, glassmorphism, неона, чрезмерных скруглений, случайных иконок, тяжёлых теней и типичных шаблонных блоков. Шрифты: современный кириллический sans-serif с локальным хостингом и корректным лицензированием, резервные системные шрифты. Определить шкалу типографики, spacing, радиусы, ширину контента и состояния интерактивных элементов.

## 4. Информационная архитектура и секции
Порядок секций:
1. Header: логотип/текстовый знак «КОНТ-ЛИДЕР», якорная навигация («Каталог», «Преимущества», «Доставка», «Контакты»), контактный телефон из конфигурации, CTA «Получить расчёт». На мобильном — компактный header и доступное меню, если требуется. Sticky header допустим, если не перекрывает контент.
2. Hero: один H1 с главным коммерческим предложением (пример, требующий подтверждения географии: «Морские контейнеры 20 и 40 футов в Москве»), короткий подзаголовок, две CTA («Подобрать контейнер», «Получить расчёт»), крупное изображение контейнера/терминала, несколько подтверждённых преимуществ (до подтверждения — нейтральные формулировки без неподтверждённых обещаний). Композиция должна выглядеть профессионально на 1440 px и мобильном 390 px.
3. Каталог: секция «Контейнеры в наличии» с карточками 20 и 40 футов (новые/БУ только если действительно доступны), фото-заглушка, название, состояние, характеристики, цена или «Цена по запросу», кнопка «Уточнить наличие». Все карточки формируются из типизированного массива данных, а не копируются вручную. Цены-заглушки не выдавать за реальные.
4. Преимущества: 3–5 кратких преимуществ, без выдуманных цифр и заявлений; иконки должны быть согласованными, допускается CSS/SVG.
5. Доставка: информация о способе расчёта, регионах, терминалах и условиях; пока реальные данные отсутствуют — текст-заглушки в централизованной конфигурации. Кнопка расчёта доставки.
6. FAQ: 4–6 реально полезных вопросов (как выбрать размер, состояние, доставка, оплата, осмотр), ответы без неподтверждённых обещаний. Доступный accordion по желанию, контент должен оставаться доступным поисковым системам.
7. CTA/форма заявки: сильный коммерческий блок «Рассчитаем стоимость контейнера с доставкой», поля имя, телефон, интересующий контейнер (если выбран), комментарий по желанию, согласие на обработку персональных данных. Ясные состояния загрузки, успеха и ошибки.
8. Контакты: кликабельные `tel:`, `mailto:`, мессенджеры только если клиент предоставил данные, адрес/режим работы при наличии. Не вставлять фальшивую карту или адрес.
9. Footer: навигация, контактная информация, ссылка на политику конфиденциальности и информацию об обработке персональных данных, юридические данные при предоставлении.

Добавить ссылки на политику и согласие. Если юридические тексты ещё не предоставлены, создать явно обозначенные черновые страницы/заглушки и пометить как блокирующее условие перед production-публикацией; не придумывать юридические документы от имени клиента.

## 5. Адаптивность и доступность
- Mobile-first. Поддержка 320 px и выше, контрольные размеры 320, 375, 390, 430, 768, 1024, 1280, 1440, 1920.
- Проверить промежуточные ширины: не должно быть горизонтального скролла, обрезанного текста, наложений, слишком мелких элементов.
- Сетка каталога: 1 колонка на узких мобильных, 2 на планшетах, 3–4 на широких экранах, исходя из фактического контента.
- Удобные touch targets, видимые `:focus-visible`, клавиатурная навигация, корректные labels, сообщения ошибок, alt для содержательных изображений, декоративным — пустой alt.
- Модальное окно заявки: управление фокусом, закрытие по Escape и кнопке, восстановление фокуса после закрытия, запрет взаимодействия с фоном, корректный `aria`-контекст. Использовать доступный нативный `<dialog>` или проверенную лёгкую реализацию.
- Уважать `prefers-reduced-motion`; не применять тяжёлые анимации.

## 6. Архитектура компонентов и данных
Пример структуры (адаптировать к текущему проекту и Nuxt 4):
```
app/
  assets/styles/        # tokens, globals, mixins при необходимости
  components/
    layout/             # AppHeader, AppFooter
    sections/           # HeroSection, CatalogSection, AdvantagesSection,
                        # DeliverySection, FaqSection, ContactSection
    catalog/            # ContainerCard
    lead/               # LeadModal, LeadForm
    ui/                 # только реально переиспользуемые элементы
  pages/index.vue
  pages/privacy.vue     # черновик, не считать готовым юридическим документом
  data/containers.ts
  data/site.ts
  types/container.ts
  types/lead.ts
  utils/formatPrice.ts
server/api/lead.post.ts
public/images/
nuxt.config.ts
```
Не создавать пустые абстракции и папки «на будущее». `ContainerCard` принимает props и эмитит `select`, не отправляет запросы самостоятельно. `CatalogSection` отображает массив и пробрасывает выбор. Страница (`index.vue`) владеет общим состоянием выбранного контейнера и открытием общей модалки, потому что её могут открывать и Hero, и Catalog. `LeadForm` владеет локальными полями, ошибками и состоянием отправки, если оно не нужно другим компонентам. Pinia не требуется. Данные каталога, контакты, SEO-тексты, изображения и ссылки хранить централизованно и типизированно, чтобы их можно было быстро заменить при получении материалов клиента.

## 7. Форма заявки и сервер
- Одна переиспользуемая форма, доступная из Hero, карточек каталога и CTA-блока. Выбранный контейнер автоматически подставляется, если он есть; форма работает и без выбранного контейнера.
- Поля: имя, телефон, containerId (опционально), комментарий (опционально), согласие (обязательно). Проверка на клиенте ради UX и на сервере ради безопасности. Проверять длины и формат, нормализовать ввод, не доверять данным клиента.
- POST `/api/lead`: принимать только ожидаемые поля, ограничивать размер payload, валидировать, применять разумную защиту от спама/rate limiting, корректно отвечать без утечки внутренних деталей.
- Интеграция доставки заявок — через конфигурируемый серверный адаптер (Telegram/email/CRM), но не придумывать рабочие токены. Если секреты не заданы, НЕ имитировать успешную отправку: показывать честную ошибку или явно обозначенный dev-only режим.
- Telegram Bot Token и Chat ID (если выбрана Telegram-интеграция) хранить исключительно в server runtime config/env; не в клиентском bundle и не в Git. Бот должен иметь разрешение отправлять сообщения в целевой чат.
- Не логировать телефоны, секреты и другие персональные данные без необходимости. Не добавлять внешнюю аналитику без согласования.
- При статическом деплое без Nitro endpoint не будет работать: либо выбрать Node/Nitro-хостинг с prerender главной страницы, либо отдельную serverless-функцию. Явно документировать выбранный вариант.

## 8. SEO с первого этапа разработки
Техническое SEO должно быть встроено в реализацию, а не добавлено после завершения.

### Рендеринг
- Nuxt route rule `'/': { prerender: true }` при подходящей конфигурации хостинга.
- Главная страница, заголовки, карточки, характеристики и основные тексты должны присутствовать в исходном HTML после сборки, а не появляться только после клиентской гидратации.
- Проверить `npm run generate` или соответствующий production build и реально инспектировать полученный HTML.

### Семантика
- `html lang="ru"`, один основной H1 на странице как выбранная конвенция проекта, логичная иерархия H2/H3.
- Использовать `header`, `nav`, `main`, `section`, `article`, `footer`, `button`, `a` по смыслу. Не превращать навигацию в `div` с click handlers.
- Реальные тексты, названия и цены — HTML, не текст внутри изображений.
- Чистые человекочитаемые якоря и корректная работа переходов к секциям с учётом sticky header.

### Meta
- `useSeoMeta` для title, description, ogTitle, ogDescription, ogType, ogImage, twitterCard при необходимости.
- Canonical через `useHead`, использовать единый конфиг базового URL сайта; до получения домена не подставлять фиктивный production URL как настоящий.
- Favicon, web manifest при необходимости, превью соцсетей.
- Уникальный title и description для главной и дополнительных страниц.
- Предварительный вариант title (уточнить по региону и ассортименту): «Купить морской контейнер в Москве — 20 и 40 футов | КОНТ-ЛИДЕР».
- Предварительный description: «Морские контейнеры 20 и 40 футов: новые и Б/У. Подбор контейнера и расчёт доставки. Уточните наличие и стоимость.» Не обещать услуги, которые заказчик не подтвердил.

### Индексация
- `robots.txt` с корректной ссылкой на sitemap.
- `sitemap.xml` с реальными публичными URL (можно вручную для маленького сайта).
- Не индексировать технические маршруты и служебные ответы; не допускать случайного noindex для главной на production.
- Проверить корректные HTTP-статусы, отсутствие битых ссылок, редиректы www/non-www и HTTP→HTTPS на хостинге, отсутствие дублей URL.
- Подготовить инструкции для подключения Яндекс Вебмастера и Google Search Console.

### Structured data
- Добавить корректную JSON-LD разметку `Organization` или подходящий `LocalBusiness` только при наличии реальных данных, не выдумывать адрес и рейтинг.
- При наличии подходящих данных допустима разметка `Product` для карточек, но не создавать фиктивные отзывы, цены и наличие.
- Проверить JSON-LD валидатором и убедиться, что данные совпадают с видимым контентом.

### Контентная стратегия
- Основной запрос — коммерческая продажа морских контейнеров в подтверждённом регионе; уточнить географию клиента.
- Подразделы раскрывают 20/40 футов, состояние, доставку, выбор и FAQ. Не заниматься переспамом ключевыми словами.
- Одностраничник не гарантирует высокие позиции по множеству разных запросов; предусмотреть возможность дальнейшего расширения на отдельные категории и страницы без переписывания архитектуры.
- Никаких обещаний топ-1, гарантированной индексации или определённого SEO-трафика.

## 9. Производительность
- Цель: хорошие реальные Core Web Vitals: LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1 на 75-м процентиле; Lighthouse использовать как лабораторную диагностику, а не гарантию.
- Оптимизировать фотографии: WebP/AVIF, responsive sizes, известные размеры/aspect-ratio, lazy loading для изображений ниже первого экрана.
- Hero/LCP-изображение НЕ lazy-load; настроить приоритет загрузки при необходимости.
- Минимизировать JS, не подключать тяжёлые библиотеки ради простых эффектов.
- Локальные оптимизированные шрифты, `font-display`, исключение ненужных начертаний.
- Исключить скачки layout и ненужные запросы.

## 10. Тестирование и критерии приёмки
- Сайт корректно отображается от 320 до 1920+ px, без горизонтального скролла и наложений.
- Визуальная иерархия соответствует дизайн-концепции: светлый промышленный минимализм, графит + терракота, без AI-шаблонности.
- Все навигационные ссылки, CTA, меню и модальное окно работают с мышью, клавиатурой и на touch.
- Карточки генерируются из типизированных данных; отсутствие фотографии не ломает layout.
- Выбор контейнера из карточки открывает форму с правильным containerId; Hero открывает форму без обязательного выбора.
- Клиентская и серверная валидация работают; состояния loading/success/error честно отображаются; ошибки API обработаны.
- При отсутствующей интеграции заявка не считается успешно доставленной.
- Метатеги, canonical, sitemap, robots, alt, заголовки и JSON-LD проверены.
- Production HTML главной содержит индексируемый контент.
- Проверены TypeScript, lint, production build; тесты запускаются при наличии.
- Отсутствуют секреты в клиентском коде и Git.
- Предоставлен README с командами запуска, сборки, env, деплоя, обновления каталога, фотографий и контактов.
- В финальном отчёте перечислить выполненное, реально запущенные проверки, известные ограничения и материалы, которые нужны от клиента.

4. Реализуй каталог из типизированных данных и карточки.

8. Проверь доступность, мобильные состояния, performance.
